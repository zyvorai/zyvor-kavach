# Research: how vendors detect, and what Kavach should add

Researched 2026-11-23. Research only; the build that followed is [web-detection.md](web-detection.md). Scope: endpoint and XDR, WAF/API/bot/DDoS, network detection and response (NDR), and open detection content. Kavach is observation only: it detects and reports, never contains; it never calls a cloud API, scans a host or fetches a link; it analyses audit logs, SBOMs, messages and artifacts that users send it, offline ([architecture.md](architecture.md), [competitive-analysis.md](competitive-analysis.md)). Ideas below were filtered through that boundary first.

How to read the evidence. Vendor rows come from marketing or documentation pages fetched on the date above (marked **[fetched]**), from a search result summary (**[search]**), or from general knowledge of the product that no fetched page confirmed (**[unverified]**). Vendor performance claims (accuracy, "near zero false positives", "N days before disclosure") are the vendors' and were not tested. No proprietary rule content, and nothing from a licensed rule set, was copied; the rules that came out of this are original and cite concepts only.

What Kavach already has here: host process, file, network, registry, DNS, auth and module rules (1,475 embedded rules in 12 packs plus the 49 added by this work, [content-framework.md](content-framework.md)), custom content and Sigma import ([sigma-import.md](sigma-import.md)), kavach-seq sequence hunting (an EQL-like language), behaviour and beacon models ([local-models.md](local-models.md)), ransomware and identity (ITDR/UEBA) modules, causality-like storylines and incidents, case management, a validation lab, rule health and lifecycle, exceptions with mandatory expiry. Three patterns repeat across every vendor: (1) signature or rule detection of injection, traversal and exploit probes; (2) **API discovery from traffic and comparison with a declared schema**; (3) behavioural detection of bots, credential stuffing and L7 floods by counting and baselining. All three work on logs. The enforcing half (blocking, challenge, rate limiting, positive-model enforcement) is out of scope for Kavach.

What Kavach had: nothing for web logs. The closest were `auth_burst.go` (failed logins per source, from agent auth telemetry), config assessment of submitted NGINX and similar config text (`inspect_config_*`), URL and e-mail inspection of links users send, and the cloud audit pack. There was no access-log parser, no web attack rules, no API inventory, no flood summary.

## 5. Ranked ideas

Ranking is by detection value for a log-only, observation-only tool, then effort and risk. "Built" means shipped in this change.

1. **Offline web access-log attack detection (built).** Every WAF vendor and CRS lead with it; Kavach had none; works on logs the user already has (NGINX, Apache, F5, Cloudflare Logpush). Delivered as 49 content rules so versioning, lifecycle, tuning, validation and custom content apply. Concept sources: CRS attack families, vendor signature categories. Rules were authored from public descriptions of the request patterns.
2. **API discovery and shadow-API report from logs against a user-sent OpenAPI file (built).** F5 XC, FortiWeb, Imperva and Akamai all sell discovery plus a positive model. Kavach does the discovery and diffing half only (inventory, shadow, protected-but-undocumented, verb drift, undeclared query parameters, unobserved operations); it does not enforce a positive model. JSON OpenAPI only (no YAML dependency).
3. **Credential stuffing and bot summary from logs (built).** F5, Cloudflare (leaked credentials), FortiWeb and Akamai all detect it; Zeek's guesser-then-success notice is the open reference. Delivered twice: from access logs (login-path heuristics, no usernames) and from authentication logs (`/v1/auth/logs`: stuffing, distributed account attack, velocity, success after failures, impossible travel from user-supplied geo). Kavach never queries a leaked-credential service or a geo service.
4. **Flood and DDoS summary from logs (built).** Per-source and distributed HTTP flood windows with peak rate, top path and 5xx share. Behavioural DDoS is a vendor staple; as a summary over a log it is honest and cheap. It cannot see volumetric L3/L4 attacks.
5. **Enumeration and User-Agent rotation (built, small).** The scanner-behaviour half of bot detection.
6. **ATT&CK coverage-gap report with D3FEND mapping (not built).** The ATT&CK matrix already reports covered and uncovered techniques (`GET /v1/attack/matrix`, `GET /v1/content/coverage`, per-actor `exact/related/gap` in [adversary-profiles.md](adversary-profiles.md)). A separate gap report would mostly repeat that. D3FEND mapping needs a verified technique-to-countermeasure table; building one from memory would risk wrong claims, so it was not attempted. Rank: next, but needs a source-checked table.
7. **Sigma correlation rules (not built).** `event_count`, `value_count` and `temporal` map cleanly onto the windowed detectors Kavach now has built in (`web-an-*`, `auth-an-*`, `auth_burst`). A Sigma correlation importer would let users author those in a standard format. Worth doing, but it needs the stateful engine to be a framework rather than fixed constants; that is a larger design step.
8. **Threat-campaign feeds with expiry and rollback (not built).** IOC import already has expiry, per-source TTLs and stats ([ioc-import.md](ioc-import.md)); matching imported IOCs against ingested logs would be a small follow-up (client addresses and request hosts from the new parsers are now available). Rollback by source is the missing piece.
9. **Rule maturity tiers and replay corpora (partly present).** Falco-style tiers exist as lifecycle states; Splunk-style `attack_data` replay would be the web fixtures in `testdata/web` growing into a labelled corpus. Needs real logs from users, which cannot be shipped.
10. **Entity-grouped alerts across new sources (future).** Corelight and Cortex group alerts by entity; Kavach groups by host. Web findings use a `web:<vhost>` host label and carry the client in `destination`, so grouping by client address is possible but not exposed in the UI.

Rejected, with reasons: attack disruption, SOAR-style response, anti-exploit mitigations and CryptoGuard-style process killing (response and prevention, forbidden by the boundary); crawling or probing the user's APIs for discovery (Kavach never fetches); querying leaked-credential or IP-geo services (Kavach never calls outside services for analysis); anomaly-score blocking à la CRS (observation only; the severity field plays the scoring role); per-customer unsupervised deep-learning baselines (Darktrace, ExtraHop: not verifiable or testable offline in this scope, and Kavach's existing local models cover a narrow slice).

## 6. Caveats

* Several vendor pages are marketing summaries; where a page did not name a capability it is marked as not stated, not as absent.
* SentinelOne, Vectra and ExtraHop product pages could not be fetched (HTTP 429 or 404); those rows rest on search-result summaries and are marked **[search]**.
* The Palo Alto network detection row and the claim "SentinelOne static AI works like X" were not verified.
* Rule counts and thresholds in the Kavach implementation are Kavach's own choices, not vendor numbers; the CRS and Zeek numbers quoted above are the only figures taken from a source.
