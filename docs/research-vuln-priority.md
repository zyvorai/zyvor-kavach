# Research: evidence-based vulnerability prioritisation

Date of research: 2026-11-13. "Opened" means the page or file was actually fetched and read during this work. Summaries are in our own words. Nothing below is invented; where a page did not state something, that is said.

## Sources opened

### 1. CISA, "CISA Stakeholder-Specific Vulnerability Categorization Guide", November 2022
URL: https://www.cisa.gov/sites/default/files/publications/cisa-ssvc-guide%20508c.pdf (the older us-cert.gov URL 301-redirects here). Opened as a PDF and read as text.
CISA's customised SSVC tree has four outcomes (Track, Track*, Attend, Act) and five decision points: exploitation (none, public PoC, active), technical impact (partial, total), automatable (no, yes), mission prevalence (minimal, support, essential) and public well-being impact (minimal, material, irreversible). Table 8 folds the last two into one "mission and well-being" value (low, medium, high); Table 9 is the 36-row decision table from exploitation x automatable x technical impact x mission-and-well-being to an outcome. The guide says it has no "unknown" value: where evidence is missing, the analyst picks the most reasonable assumption from prior events. It says mitigation status is tracked but does not change the decision, and that exploitation answers should be time-stamped and describe the present state, not a prediction. Kavach's evaluator (`vuln_prio_ssvc.go`) transcribes Tables 8 and 9 and the unit test checks all 108 input combinations against an independent copy of Table 9.

### 2. Spring, Householder, Hatleback, Manion, Oliver, Sarvepalli, Tyzenhaus, Yarbrough, "Prioritizing Vulnerability Response: A Stakeholder-Specific Vulnerability Categorization (Version 2.0)", SEI/CMU, 30 April 2021
URL: https://www.sei.cmu.edu/library/prioritizing-vulnerability-response-a-stakeholder-specific-vulnerability-categorization-version-20/ (library landing page and abstract only; the full report PDF was not opened).
The abstract presents SSVC as a modular decision system for vulnerability management that avoids one-size-fits-all scoring by letting each stakeholder choose well-defined decision points. Version 2.0 adds a coordinator perspective, refines terminology and adds tooling. We rely on the abstract only for the provenance of SSVC; the actual tree we implement comes from source 1.

### 3. FIRST, "EPSS FAQ"
URL: https://www.first.org/epss/faq
EPSS estimates the probability that a CVE will be exploited in the wild in the next 30 days, as a number from 0 to 1 plus a percentile, updated daily. The page stresses that it is not a complete risk score: it ignores impact, your assets and compensating controls. It warns against multiplying EPSS by CVSS, and calls them separate signals. Scores are free with no registration; the page says attribution is requested when EPSS is used in publications or products and names no data licence. Model updates follow performance degradation, roughly annually, and the CSV's first line is a `#` comment naming the model version.

### 4. FIRST, "EPSS data" page
URL: https://www.first.org/epss/data
The stable daily bulk file is `https://epss.empiricalsecurity.com/epss_scores-current.csv.gz` (it redirects; gzip CSV with `cve`, `epss`, `percentile`; v2+ files start with a `#` comment giving model version and date). The API at `https://api.first.org/epss/` is described as "designed for lookup, not bulk access". Terms: the page says scores are published daily, free, no registration, and gives the attribution text "EPSS is maintained by the EPSS Special Interest Group at FIRST. Scores are generated by Empirical Security and published freely to the community." No specific licence or commercial-use terms were stated on the page. (First attempt timed out; second succeeded.)

### 7. Jacobs, Romanosky, Suciu, Edwards, Sarabi, "Enhancing Vulnerability Prioritization: Data-Driven Exploit Predictions with Community-Driven Insights", arXiv:2302.14172 (v1 27 Feb 2023, v2 15 Jun 2023)
URL: https://arxiv.org/abs/2302.14172 (abstract page only; the PDF was not opened).
The abstract argues severity-based prioritisation predicts exploitation poorly and that many alternatives are proprietary, so a community SIG (170+ experts) built an open, data-driven scoring system. It reports that the new model is 82% better at separating exploited-in-the-wild vulnerabilities than earlier ones. The abstract does not name "v3", nor give features, data or the metric behind the 82%, so we do not quote those; a snippet from the search result said PR-AUC 0.779 versus 0.429, which we did not verify in the paper itself and do not rely on.

### 8. Jacobs, Romanosky, Edwards, Roytman, Adjerid, "Exploit Prediction Scoring System (EPSS)", arXiv:1908.04856 (13 Aug 2019)
URL: https://arxiv.org/abs/1908.04856 (abstract page only).
The first EPSS paper, presented at Black Hat 2019, proposes an open data-driven framework that estimates the probability a vulnerability is exploited in the wild within twelve months of disclosure. It is meant to be updated as better data appears. Note the horizon: the 2019 model used twelve months; the current FAQ (source 3) says 30 days.

### 9. FIRST, "CVSS v3.1 Specification Document"
URL: https://www.first.org/cvss/v3.1/specification-document
Base metrics are AV, AC, PR, UI, Scope, C, I, A, written as `CVSS:3.1/AV:N/AC:L/...`; all eight are mandatory, temporal and environmental ones default to Not Defined. Qualitative bands: None 0.0, Low 0.1-3.9, Medium 4.0-6.9, High 7.0-8.9, Critical 9.0-10.0. The base score reflects intrinsic severity assuming a reasonable worst case, and business factors (customers affected, monetary loss, life and property) are explicitly outside CVSS. Kavach uses the vector only to approximate SSVC automatable and technical impact.

### 10. FIRST, "CVSS v4.0 Specification Document"
URL: https://www.first.org/cvss/v4-0/specification-document
v4.0 has Base, Threat, Environmental and Supplemental groups, with the nomenclature CVSS-B, BT, BE, BTE so a reader knows which groups fed a score. Exploit Maturity (Attacked, PoC, Unreported) is a Threat metric; Automatable (Y/N) is a Supplemental metric defined via the same four kill-chain steps SSVC uses, and supplemental metrics do not change the score. The v4 vector uses AT, VC/VI/VA, SC/SI/SA. Kavach uses AU verbatim when a v4 vector carries it.

### 11. CISA, "Known Exploited Vulnerabilities Catalog"
URL: https://www.cisa.gov/known-exploited-vulnerabilities-catalog
CISA calls it the authoritative source of vulnerabilities exploited in the wild and says organisations should use it as an input to prioritisation. Entries show date added, due date, a ransomware-use flag (Unknown/Yes/No) and, on the page we saw, a reference to BOD 26-04 for mitigation and forensic triage; the page did not mention BOD 22-01 or list inclusion criteria. That is why KEV membership maps to SSVC Exploitation = active and takes precedence over EPSS.

### 12. Tenable documentation, "CVSS vs. VPR"
URL: https://docs.tenable.com/vulnerability-management/Content/Analysis/RiskMetrics.htm (documentation only, as requested).
VPR is a Tenable-calculated 0.1-10.0 score refreshed daily as a "dynamic companion" to CVSS, banded Low/Medium/High/Critical. Listed drivers include exploit code maturity, exploit probability, news and malware observation recency and intensity, KEV membership, and targeted industries. Tenable says these drivers reflect the global threat landscape and are not tailored to an organisation, and the formula is not published. A vendor claim, not an independent evaluation; Kavach does not copy it.

### 13. Allodi and Massacci, "My Software has a Vulnerability, should I Worry?", arXiv:1301.1275
URL: https://ar5iv.labs.arxiv.org/html/1301.1275 (HTML rendering of the paper, summary opened).
Compares NVD/CVSS with exploit-database and exploit-kit data against Symantec's in-the-wild data. It concludes CVSS alone is a poor test for exploitation (high sensitivity, poor specificity), estimates only about 3-4% risk reduction from patching purely by high CVSS, and finds presence in black-market exploit kits far more informative. The data are from roughly 2013, so numbers may not hold today; the qualitative point matches the EPSS and CISA guidance.

## Design consequences

- Feed choice: the bulk file, not the API. A bulk GET reveals nothing about this install, whereas per-CVE API queries would disclose which CVEs matched. Filtering happens locally.
- EPSS maps to SSVC only as exploitation evidence: at or above 0.10 it counts as `poc`-level evidence. 0.10 is a Kavach policy choice; neither the SSVC guide nor FIRST defines such a cut. A low EPSS leaves exploitation `unknown` (not `none`) because a low probability is not proof that no exploit exists.
- KEV wins over EPSS because KEV is observed exploitation, EPSS is a forecast.
