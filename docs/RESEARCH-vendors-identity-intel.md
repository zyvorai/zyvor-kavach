# Research: identity, email, threat intelligence, SIEM, deception, ransomware and data-security vendors

Researched 2026-11-23. Research only; the build that followed is described in [identity-detection.md](identity-detection.md), [exploit-intel.md](exploit-intel.md), [ransomware-logs.md](ransomware-logs.md) and [tripwires.md](tripwires.md). This continues [RESEARCH-vendors-detection.md](RESEARCH-vendors-detection.md) (endpoint, WAF, NDR) and [RESEARCH-vendors-posture.md](RESEARCH-vendors-posture.md) (posture); it does not repeat them.

Kavach is observation only: it detects and reports, never contains; it never calls a cloud, identity-provider or threat-intelligence API, scans a host or fetches a link; it analyses logs, exports, feeds and artifacts users send it, offline ([architecture.md](architecture.md)). Every idea below was filtered through that boundary first.

How to read the evidence. **[fetched]** means the claim was read on a fetched page on the date above. **[search]** means it came from a search-result summary only. **[U]** means unverified: from general knowledge, no page was read for it. Vendor claims about accuracy or "AI" were not tested. No vendor, Sigma, Elastic or other licensed rule text was copied; the rules built from this are original and cite concepts only.

Cross-vendor pattern for log-based identity analytics: the same dozen behaviours recur. A burst of denied or repeated MFA prompts followed by a success (push fatigue, abuse of an approval). One source against many accounts with few tries each (spray). Geovelocity. Sign-in from a context never seen for the account followed by a security-relevant change. Administrator-role grants. New authentication method after a reset. Legacy protocols that bypass MFA. Session or token reuse from a second place. Dormant-account reactivation (Sentinel UEBA flags accounts unused for 180 days). Provider-computed risk on a successful sign-in. All of these work on exports; the enforcing half (step-up, block, revoke) is out of scope.

What Kavach already had: `/v1/auth/logs` (generic auth records: stuffing, distributed attack, velocity, success after failures, impossible travel from supplied geo, [web-detection.md](web-detection.md)); the agent-fed ITDR module (`identity-password-spray`, `identity-impossible-travel`); cloud audit normalisation with an Okta and M365 slice ([cloud-audit.md](cloud-audit.md), `cld-` rules). What was missing: Okta and Entra field mapping with event semantics (deny push, privilege grant, factor activation, consent, session ids), sequence logic across event kinds, and role-grant analytics.

## 2. E-mail security

| Vendor | Notable detections (paraphrased) | Mark | Source |
|---|---|---|---|
| Microsoft Defender for Office 365 | Spoof intelligence from composite authentication (compauth) plus intent; "honor DMARC" (act on p=quarantine or reject); user impersonation (protected senders), domain impersonation (similar domains, other TLDs, Unicode lookalikes), mailbox intelligence from communication history; safety tips (first contact, impersonation, unauthenticated "?"). | BIMI (concept) | Needs DMARC at enforcement and, for major inboxes, a certificate; IETF draft. | [search] | https://www.ietf.org/archive/id/draft-brotman-ietf-bimi-guidance-15.html |
| Proofpoint | Supplier Risk Explorer scores supplier domains, including malicious lookalikes of suppliers; Supplier Threat Protection learns normal communication per supplier and flags a change even from authenticated domains; BEC types (gift card, payroll redirect, invoice). | [search] | https://www.proofpoint.com/us/solutions/cyber-supply-chain-risk-management |
| Mimecast | Relationship graphing and intent classification; link and QR protection through redirects; sandboxing. Marketing level, no named detections. | [fetched] | https://www.mimecast.com/products/email-security/ |
| Abnormal Security | Behavioural baselines of communication, vendor email compromise with payment-behaviour baselines, account takeover from combined login signals. | [search] | https://abnormal.ai/learning/behavioral-ai-email-security |

Kavach's existing message analyser ([url-email-inspection.md](url-email-inspection.md)) already covers: Authentication-Results and Received-SPF reading (spf, dkim, dmarc, arc, compauth), From, Reply-To, Return-Path and Sender mismatch, display-name brand and address spoofing, lookalike sender domains through the domain analyser, Message-ID and Received-chain checks, HTML link and form tricks, QR hints, attachments. Vendor-side behavioural baselines (per-recipient history, supplier graphs, mailbox intelligence) need mailbox data Kavach never sees. **Result: no clear gap for single-message analysis, so candidate (e) was not built.** The one real gap is a different artifact: DMARC aggregate (RUA) reports that domain owners already receive, which show unauthorised senders and alignment failures per source. That is recorded as an idea (rank 6 below), not built here.

## 7. Ranked ideas

Ranked by detection value for a log-only, observation-only tool, then effort and risk.

1. **Identity-provider log analytics for Okta and Entra exports (built).** Every identity vendor in section 1 leads with the same behaviours and all of them work on exported logs. Delivered as `idp-an-*` analytics: [identity-detection.md](identity-detection.md).
2. **Offline KEV and EPSS import with versioning, expiry and transparent weighting (built).** Removes the need for any Kavach-initiated network feed to get exploit likelihood; feeds SSVC, SBOM matches and attack paths: [exploit-intel.md](exploit-intel.md).
3. **Ransomware and backup log analytics (built).** Closes the gap between the process-event detector and the file-server and backup-server logs users actually have: [ransomware-logs.md](ransomware-logs.md).
4. **Declared tripwire registry for honey accounts, decoy values, hosts, IPs and paths (built).** Cheap and high fidelity (any use of a decoy is suspicious): [tripwires.md](tripwires.md).
5. **SIEM export mapping (already built).** OCSF class uids were re-verified; nothing to add.
6. **DMARC aggregate (RUA) report analysis (not built).** XML (often gzip or zip) per reporting organisation with source IP, volume, SPF and DKIM results and alignment, disposition. It would show unauthorised senders and misaligned legitimate ones. Real value, a new artifact type; needs a decompression-bomb-safe XML reader and a source-IP report. Next candidate for the e-mail area.
7. **Sigma correlation rules (not built).** `event_count`, `value_count` and `temporal` map onto the windowed detectors Kavach now has in several places (`web-an-*`, `auth-an-*`, `idp-an-*`, `rwlog-an-*`), but a generic importer needs a stateful engine as a framework, not constants in each analyser. Larger design step.
8. **UEBA-style per-entity risk accumulation (RBA) across analytics (not built).** An entity score summing findings per user over a window would unify the new analytics; the attack-path score is the closest existing piece.
9. **MISP warninglists and sightings-based decay for IOC import (not built).** Would cut false positives; needs the warninglist content, which is licensed per list.

Rejected, with reasons: containment features of every vendor (universal logout, session termination, credential rotation, quarantine, account isolation, restore: forbidden by the boundary); calling Entra, Okta, VirusTotal, Recorded Future, Mandiant or MISP servers (Kavach never calls an outside service for analysis); leaked-credential checking (needs a service); domain-controller protocol analytics such as DCSync or golden ticket detection (needs DC telemetry that this path does not receive); mailbox-intelligence and communication-graph baselines (need mailbox data); entitlement outlier scoring (needs IGA data); content-based entropy analysis (Kavach reads logs, not file content; entropy is only relayed from a field); per-customer deep-learning baselines (not verifiable offline here).

## 8. Boundaries checked

- No code path in the new analytics opens a network connection; the exploit-intel import reads the request body only.
- Allow-listed fields only; tokens, passwords and secrets are never read or stored; decoy token values are masked in API output and absent from findings.
- Findings are advisory; no guidance text claims an automatic action (the guidance catalog test enforces this).
- Stdlib only; no change to `go.mod`, `go.sum`, Dockerfiles or workflows.
- Original rules; vendor and standard names appear as concepts and citations only.

## 9. Caveats

- Several vendor rows rest on search summaries or marketing pages (marked); the [U] rows (Recorded Future, Mandiant, Anomali, Chronicle, Elastic, Exabeam, Securonix, XSOAR, Illusive, Attivo, Halcyon, Cyera, BigID, MISP, STIX detail) were not read from a page.
- The Okta field names for geography, user agent and `security.threat.detected` were not verified on the pages read; the parser accepts them tolerantly and the tests use shapes written from the verified names plus these assumptions.
- The Entra MFA-denied error code 500121 and the Okta `debugData.privilegeGranted` key are unverified [U].
- Entra audit names changed over the years and tenants differ; the matcher uses substrings of the activity name, so unusual or localised names will be missed.
- All thresholds (counts, windows, EPSS policy cut-offs of 0.10 and 0.50) are Kavach's own choices, not vendor or FIRST numbers.
